# The input-method popup surface

Decided 2026-10-20, built on Linux for Wayland-native applications (Brave, Firefox, GTK, Qt) where Fcitx5 cannot tell where the text cursor is.
The self-drawn candidate window of [candidate-window.md](candidate-window.md) is shown inside the `zwp_input_popup_surface_v2` that the compositor places at the caret.

## Why

Fcitx5's Wayland frontend gets no cursor rectangle from the compositor: `input-method-v2` has no such event. The compositor does know it (the client sends it to the compositor with `text-input-v3`), and places the popup surface of the input method exactly, flipping it at screen edges. A layer-shell window positioned by the Server therefore only works where the rectangle is known (XWayland and X11 clients, global coordinates). For a Wayland-native client the plugin sees an all-zero rectangle and the window used to fall back to Fcitx5's panel.

## What a spike showed (Fcitx5 5.1.22, Hyprland 0.56, Brave 1.95, 2026-10-20)

- An addon can get the input-method object of a `wayland_v2` input context: `FCITX_ADDON_DECLARE_FUNCTION(WaylandIMModule, getInputMethodV2, fcitx::wayland::ZwpInputMethodV2 *(fcitx::InputContext *))` matches the signature of `waylandim_public.h`, which Fcitx5 does not install. The result is an opaque pointer to Fcitx5's C++ wrapper, whose classes are in static libraries and not installed.
- The raw `zwp_input_method_v2` proxy is found inside the wrapper without knowing its layout: the wrapper stores itself as the proxy's user data, so a pointer-sized word `p` of the wrapper that is readable, has `wl_proxy_get_user_data(p) == wrapper` and `wl_proxy_get_class(p) == "zwp_input_method_v2"` is the proxy. On 5.1.22 it is the 17th word. Readability is checked with `process_vm_readv` before dereferencing.
- With the proxy, the addon calls the C function `zwp_input_method_v2_get_input_popup_surface` (bindings generated by `wayland-scanner` from the protocol XML) on a `wl_surface` of its own, created on a private event queue, and attaches a `wl_shm` buffer.
- Brave sends `set_cursor_rectangle` only while an input method composes; Hyprland then places the popup below the caret and reports `text_input_rectangle` to it. Before the first composition the compositor has a placeholder rectangle, which does not matter because the window is shown only while composing.
- Fcitx5 crashed once inside `libclassicui` while the test browser was killed; it was not reproduced and not attributed. The real addon keeps the Fcitx5 panel empty while the popup shows and destroys the popup before anything else takes over.

## Where it lives

No Fcitx5 UI addon. Only one UI addon is active and it would replace classicui for every input method; our engine addon already runs inside Fcitx5, already leaves the panel empty for frames the Server draws, and can create the popup itself. Selecting nothing, falling back automatically.

- Plugin (`apps/linux/fcitx5/src/popup/`): finds the proxy, owns the private Wayland queue (compositor, shm, optionally viewporter and fractional-scale), creates and destroys the popup surface, attaches buffers. A `Presenter` interface hides the Wayland part from the tests.
- Server (`apps/linux/server/src/popup/`): a render thread with the renderer and the theme, a pool of shared-memory buffers, animation pacing.
- Protocol: a second connection to the same socket, the popup channel (below). The key path is unchanged: the reply to a key only says `native`.

## Popup channel

The plugin opens a second connection and sends `Attach {protocol, token}`; `token` is random per plugin instance. `Open` carries the same token as `popup` when the context is a `wayland_v2` one whose popup can be created. The Router then hands the frames of that session to the popup hub instead of the layer-shell window. Frames are drawn on the render thread so typing never waits for them.

Server to plugin (JSON frames as on the main connection; `Pool` carries a file descriptor in `SCM_RIGHTS` ancillary data):

- `Pool {pool, size}` + fd: a `memfd` holding the slots. The plugin passes the descriptor to `wl_shm.create_pool`; no pixels are copied by the plugin.
- `Present {context, pool, buffer, offset, width, height, stride, scale_120, logical_width, logical_height}`: draw this buffer for the input context `context`. The plugin makes a `wl_buffer`, attaches it, sets the viewport destination to the logical size (or `set_buffer_scale` without viewporter) and commits.
- `Hide`: destroy the popup surface.

Plugin to Server: `Released {buffer}` when the compositor released the buffer, or the plugin dropped it unshown; `Scale {scale_120}` when the preferred scale of the popup changes (`wp_fractional_scale_v1`, else the integer output scale, times 120).

The Server keeps three slots; a frame is skipped when all are in use. A bitmap bigger than a slot starts a new pool. Animation: while `Rendered::next_frame` is set the render thread draws the next frame at its deadline and presents it, and it stops completely when the animation ends or the window is hidden, so an idle window costs no wake-ups.

## The shape of the bitmap

The compositor puts the top-left corner of the popup at the caret. The popup therefore shows the card only: the bitmap is cropped to the content rectangle and a shadow would show as a tint in the rounded corners, and the parts of decorations that hang over the card (the Sakura blossom) are cut off. The Sakura theme therefore has no shadow and a 2 pt border. A theme variant that fits is possible later.

## Which window shows what

| Context | Window |
|---|---|
| `wayland_v2`, popup created, channel attached, `mode` not `native`/`fcitx` | popup surface |
| X11 or XWayland with a known rectangle | layer-shell window |
| anything else, or any failure | Fcitx5's panel |

`[panel] mode`: `auto` picks as the table says, `popup` uses the popup only (Fcitx5's panel otherwise), `native` the layer-shell window only, `fcitx` Fcitx5's panel.

## Limits and risks

- **Fcitx5 crashes on a surface of its connection that it did not make, when the pointer or a finger meets it.** `classicui` turns the surface of a `wl_pointer.enter` into its wrapper object through the proxy's user data and calls `userData()` on it; for the popup surface that is a null pointer, and Fcitx5 dies (the keyboard goes with it until it is restarted). The popup surface therefore carries a zeroed guard block as its user data (`popup/wayland/guard.h`), which makes the handler take its "not my window" return. Seen once on a real session before the guard; after it a pointer swept over a visible popup does nothing.
- Mouse clicks on rows do not work in the popup: compositors do not send pointer events to input-method popups. Keys select.
- GNOME has no `input-method-v2`; nothing changes there. KDE uses the v1 protocol with a cursor rectangle that Fcitx5 does receive, so the layer-shell window keeps serving it where it works; a v1 panel surface is a possible later step.
- The proxy search depends on Fcitx5 storing itself as the proxy's user data. If it ever stops, nothing is found and the feature switches itself off (logged once). The proper fix is an upstream function that exports the popup creation.
- Fractional scale on popup surfaces is not supported by every compositor; the plugin then uses the integer output scale, and a slightly soft window is the cost.
